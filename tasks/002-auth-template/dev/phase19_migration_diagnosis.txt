Дата: 2026-09-14
Режим: диагностика только; product code, `DEFECTS.md` и migration files не изменялись.
Runtime DB не использовалась: проверка upgrade выполнена с `APP__DB__URL=sqlite+aiosqlite:////tmp/phase19_isolated.db`.

## Текущая рабочая копия

Команда из `fastapi-application/`:

```text
../.venv/bin/alembic heads
../.venv/bin/alembic history
../.venv/bin/alembic current
../.venv/bin/alembic upgrade heads --sql
```

Результат всех четырёх команд: пустой вывод и exit 0. В текущем дереве каталога
`fastapi-application/alembic/versions/` есть только `.keep`; Python revisions отсутствуют.

Изолированная проверка:

```text
APP__DB__URL=sqlite+aiosqlite:////tmp/phase19_isolated.db ../.venv/bin/alembic upgrade heads
exit=0
APP__DB__URL=sqlite+aiosqlite:////tmp/phase19_isolated.db ../.venv/bin/alembic current
exit=0
sqlite tables: [('alembic_version',)]
```

Причина DEF-001/DEF-002: `alembic upgrade heads` исполняет только найденные revision
scripts. При пустом `alembic/versions` у Alembic нет head и нет upgrade operations, поэтому
создаётся служебная `alembic_version`, но не таблицы из SQLAlchemy metadata. `target_metadata`
в `fastapi-application/alembic/env.py` используется для `revision --autogenerate`, а не для
создания таблиц командой `upgrade`.

## Текущая metadata и DB URL

`fastapi-application/alembic/env.py` импортирует `Base` и вызывает
`load_model_registry()`, затем устанавливает `target_metadata = Base.metadata`; URL
переопределяется из `settings.db.url`.

`fastapi-application/db_core/model_registry.py` регистрирует ровно:

```text
['order_product_association', 'orders', 'products', 'user']
```

Колонки подтверждены текущим импортом:

```text
user: ['created_at', 'email', 'hashed_password', 'id', 'image_file', 'is_active', 'is_superuser', 'is_verified', 'username']
orders: ['created_at', 'id', 'promocode']
products: ['description', 'id', 'name', 'price']
order_product_association: ['count', 'id', 'order_id', 'product_id', 'unit_price']
```

`fastapi-application/auth_users/models.py` задаёт `User.__tablename__ = "user"` и
наследует стандартные fastapi-users UUID/email/password/status поля; дополнительные
поля: nullable `username`, `image_file` с default `default.jpg`, `created_at`.

`fastapi-application/ex_order_product/model_order_product.py` задаёт таблицы `orders`,
`products`, `order_product_association`; association ссылается на `orders.id` и
`products.id`, содержит cascade foreign keys и unique `(order_id, product_id)`.

`fastapi-application/core/config.py` читает env-файлы в порядке
`prod_db.env`, `dev_sqlite.env`, `.env`, с `env_prefix="APP__"` и nested delimiter
`"__"`. Текущий dev URL из `fastapi-application/dev_sqlite.env`:

```text
APP__DB__URL=sqlite+aiosqlite:///./one_simple.db
```

В диагностике override успешно разрешился как
`sqlite+aiosqlite:////tmp/phase19_config.db`. Конфигурация сама по себе не объясняет
отсутствие таблиц; причина в отсутствии revision scripts.

## Рекомендация оркестратору

Не восстанавливать старые chain scripts и не добавлять blog cleanup migration. Следующим
узким backend-шагом штатно создать и закоммитить одну новую initial revision через
`alembic revision --autogenerate -m ...` из текущей `Base.metadata`/registry, затем на
чистой диагностической БД выполнить `alembic upgrade heads`. Такая revision должна
создавать только текущие четыре metadata tables: `user`, `orders`, `products`,
`order_product_association`; это восстанавливает auth/order flow без runtime DB, без blog
migration cleanup и без изменения текущих auth/order semantics. В этой диагностике revision
не создавалась.
